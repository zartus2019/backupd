# backupd — резервное копирование файлов на базе rsync

[English version — README.en.md](README.en.md)

Программа резервного копирования для сервера: **источник и место хранения
копий** — каталоги на Linux или Windows (локально, по SMB, по SSH
или через rsync-демон rsyncd).
Работает по принципу [rsnapshot](https://rsnapshot.org): инкрементальные
снапшоты через `rsync --link-dest` (жёсткие ссылки), политики удержания,
расписание.

```
┌─────────────────┐        SMB (CIFS) или SSH+rsync        ┌──────────────────┐
│  Linux-сервер   │ ──────────────────────────────────────▶ │  Windows        │
│  /var/data      │   backupd (этот проект, rsync внутри)   │  D:\Backup\...  │
│  /home          │                                         │  (шара / диск)  │
└─────────────────┘                                         └──────────────────┘
        HTML-интерфейс: http://127.0.0.1:8420/
```

Возможны любые комбинации концов (каждый — Linux или Windows):

| Источник → Цель | Linux | Windows (SMB) | Windows (SSH) | rsyncd | FTP (lftp) |
|---|---|---|---|---|---|
| **Linux** | ✅ | ✅ | ✅ | ✅ | ✅ |
| **Windows (SMB)** | ✅ | ✅ | ✅ | ✅ | ❌ |
| **Windows (SSH)** | ✅ | ✅ | ❌ | ✅ | ❌ |
| **rsyncd** | ✅ | ✅ | ✅ | ✅ | ❌ |
| **FTP (lftp)** | ✅ | ❌ | ❌ | ❌ | ✅ |

Ограничения:

- rsync поддерживает только **один** SSH-конец — копирование
  «SSH → SSH» одним запуском невозможно (для одного из концов
  используйте SMB, rsyncd или локальный каталог).
- При цели **rsyncd** снапшоты всегда копируются полностью:
  `--link-dest` (жёсткие ссылки) недоступен — путь к предыдущему
  снапшоту на машине демона клиенту неизвестен.
- **FTP (lftp)** копирует только между локальным каталогом
  и FTP-сервером (SMB, SSH и rsyncd не поддерживаются). Снапшоты
  не создаются — всегда одна актуальная копия (режим «Зеркало»).

## Возможности

- **Режимы копирования** (настраиваются в HTML-интерфейсе):
  - *Инкрементальный* — снапшоты с жёсткими ссылками (`--link-dest`),
    не занимают двойной объём; полное копирование каждые N дней;
  - *Полное* — каждый снапшот независимая копия;
  - *Зеркало* — одна актуальная копия (опционально с удалением лишних файлов).
- **Источники и цели**: SMB-шара Windows (рекомендуется), SSH + rsync
  (DeltaRSync), rsync-демон (rsyncd, протокол rsync://, порт 873),
  FTP-сервер (клиент lftp, одна актуальная копия),
  локальный каталог Linux (тестирование) — для обоих концов.
- **Расписание**: вручную, каждые N минут, ежедневно в ЧЧ:ММ, раз в неделю.
- **Удержание**: последние N снапшотов + по 1 в день/неделю/месяц за N периодов
  (старые снапшоты удаляются автоматически).
- **Параметры**: исключения, сжатие, контрольные суммы, лимит скорости,
  тестовый прогон (dry-run), остановка запуска.
- **Журнал** каждого задания и история запусков; после прогона под
  строкой задания остаётся статистика: суммарное число файлов на
  источнике и сколько скопировано.
- **Авторизация интерфейса по паролю** (опционально, с возможностью отключения;
  пароль хранится в виде scrypt-хеша).
- **Push-уведомления (ntfy)** о начале и завершении каждого задания —
  на Android, Linux или Windows (публичный ntfy.sh или свой сервер в
  локальной сети).
- **Двухязычный интерфейс**: русский и английский (вкладка «Система» →
  «Язык интерфейса»; выбор хранится в `config.json`).

## Установка на Linux (сервер-источник)

```bash
# зависимости
apt install rsync cifs-utils        # Debian/Ubuntu
# или: dnf install rsync cifs-utils # RHEL/Rocky/Alma
# опционально, только для FTP-варианта:
#   apt install lftp  /  dnf install lftp

# скачать проект, например в /opt/backupd
cd /opt/backupd
python3 backupd.py --port 8420 --data-dir /var/lib/backupd
```

Интерфейс: `http://IP-сервера:8420/` (по умолчанию слушает только 127.0.0.1).

### Расширенное логирование в консоли

По умолчанию сервер выводит только базовый баннер запуска. Флаги `-v` /
`--verbose` включают подробный вывод в консоль (полезно при запуске в
терминале и при отладке; для systemd используйте `journalctl -u backupd -f`):

```bash
python3 backupd.py -v    # ключевые события
python3 backupd.py -vv   # + максимальная детализация
```

Что попадает в консоль:

| Уровень | `-v` | `-vv` | Что логируется |
|---|---|---|---|
| `INFO` | ✅ | ✅ | запуск/остановка, запуск и завершение заданий, запуски по расписанию, монтирование/отключение SMB, ошибки |
| `JOB` | ✅ | ✅ | **весь журнал каждого задания** — команды rsync, вывод rsync, размеры снапшотов, ошибки |
| `WARN` | ✅ | ✅ | HTTP-запросы с кодом 4xx (с IP и длительностью) |
| `ERROR` | ✅ | ✅ | HTTP 5xx, ошибки rsync/mount/SMB, необработанные исключения (с traceback) |
| `DEBUG` | — | ✅ | все HTTP-запросы (2xx), сохранение конфигурации/состояния, удалённые SSH-команды, расчёт следующего запуска |

Остановка (Ctrl+C или SIGTERM от systemd) корректна: сервер дожидается
окончания HTTP-запроса и отключает все смонтированные SMB-шары.

### Запуск как служба (systemd)

Готовый файл — `backupd.service` в корне репозитория:
`cp backupd.service /etc/systemd/system/ && systemctl daemon-reload &&
systemctl enable --now backupd`. Содержимое:

```ini
[Unit]
Description=backupd - rsync backup server (Linux -> Windows)
After=network-online.target

[Service]
# флаг -v — подробный вывод в журнал (journalctl -u backupd -f)
ExecStart=/usr/bin/python3 /opt/backupd/backupd.py --port 8420 --data-dir /var/lib/backupd -v
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable --now backupd
```

> Служба выполняется от root — это нужно для `mount -t cifs`
> (SMB-цели). Если root не нужен, см. раздел «Запуск без root» ниже.

### Запуск без root (монтирование через sudo)

По умолчанию backupd сам вызывает `mount -t cifs ...` — для этого нужны
root-права. Чтобы запускать сервер от обычного пользователя, добавьте флаг
`--use-sudo`: mount/umount/fusermount будут выполняться через `sudo`:

```bash
python3 backupd.py --port 8420 --data-dir /var/lib/backupd --use-sudo
```

При этом пользователю сервера нужно разрешить выполнять mount/umount
без запроса пароля. `/etc/sudoers.d/backupd` (пользователь `backupd`,
права файла 0440):

```
backupd ALL=(root) NOPASSWD: /bin/mount, /bin/umount, /usr/bin/fusermount, /usr/bin/fusermount3
```

> **fusermount / fusermount3.** Для отключения SMB-шар backupd использует
> `fusermount -u` (или `fusermount3 -u`, если в системе установлен только
> новый вариант), а затем `umount` как резервный способ. Если ни одна из
> утилит не найдена, в журнал и в консоль при запуске (с `-v`) записывается
> предупреждение: «установите пакет fuse/fuse3 (apt install fuse3 /
> dnf install fuse3)». Выбранная утилита отображается во вкладке
> «Система» («Отключение SMB»).

Флаг отображается во вкладке «Система» («Монтирование SMB») и
логируется в консоли при запуске (с `-v`).

### Доступ к интерфейсу из браузера

По умолчанию интерфейс доступен только с самого сервера (127.0.0.1).
Для доступа из браузера используйте SSH-туннель (безопасно):

```bash
ssh -L 8420:127.0.0.1:8420 user@linux-server
# затем открыть http://localhost:8420/
```

Если нужен прямой доступ, запустите с `--host 0.0.0.0`
и **обязательно** задайте пароль доступа (вкладка «Система» →
«Задать / сменить пароль»).

## Настройка Windows (место хранения)

### Вариант 1. Общая папка (SMB) — рекомендуется

1. На Windows создайте папку, например `D:\Backup`.
2. Правый клик → **Свойства → Общий доступ → Расширенный общий доступ**:
   - «Включить общий доступ…», имя шары: `backup`;
   - **Параметры доступа** — разрешите нужному пользователю
     (например, локальному `backupuser` с паролем).
3. Брандмауэр: разрешите «Файлы и принтеры (вход SMB)» для вашей подсети.
4. В backupd создайте задание: *Тип цели* → «Windows — общая папка (SMB)»,
   адрес `//ИМЯ_ИЛИ_IP_WINDOWS/backup`, пользователь и пароль.

Проверка с Linux:

```bash
mount -t cifs -o username=backupuser //192.168.1.50/backup /mnt/test
```

> **Диагностика монтирования.** Перед запуском `mount -t cifs` сервер
> автоматически проверяет: наличие программ `mount`, `sudo` (при
> `--use-sudo`) и `mount.cifs` (пакет `cifs-utils`), а также доступность
> SMB-сервера по TCP (порт 445, для `vers=1.x` — 139). При ошибке
> монтирования в журнал задания записываются полная команда, исходный
> вывод `mount` и вероятная причина на русском: неверный пароль
> (NT_STATUS_LOGON_FAILURE), запрещённый доступ, неверное имя шары,
> неподдерживаемая версия протокола (vers), недоступность сервера и т.п.
> Смотрите вкладку «Журнал» в веб-интерфейсе.

### Вариант 2. SSH + rsync (DeltaRSync)

1. На Windows включите **OpenSSH Server**:
   Параметры → Приложения → Дополнительные элементы Windows →
   «OpenSSH Server» (установить, запустить службу).
2. Установите [DeltaRSync](https://www.aitmail.com/deltarsync.html)
   (или cwRsync) так, чтобы `rsync.exe` был в системном PATH
   (проверка: `where rsync` в cmd).
3. Создайте пользователя на Windows и каталог `C:\Backup`.
4. На Linux:

```bash
ssh-keygen -t ed25519          # если ключа нет
ssh-copy-id backupuser@192.168.1.50   # или вручную:
# скопируйте ~/.ssh/id_ed25519.pub в %USERPROFILE%\.ssh\authorized_keys
# на Windows (разрешите чтение .ssh только этому пользователю!)
rsync --version -e ssh backupuser@192.168.1.50:  # тест связи
```

5. В backupd: *Тип цели* → «Windows — SSH + rsync», хост, пользователь,
   каталог `C:\Backup`.

## Вариант: rsync-демон (rsyncd)

Вместо SMB или SSH можно использовать встроенный в rsync демон
(протокол `rsync://`, порт **873**) — он подходит и как источник,
и как цель (на Linux и на Windows).

1. На машине демона создайте конфиг (пример модуля `bk` для **цели**,
   запись разрешена):

   ```ini
   # /etc/rsyncd.conf
   [bk]
   path = /backup
   comment = backup module
   read only = no
   list = yes
   auth users = backup
   secrets file = /etc/rsyncd.secrets
   ```

   `secrets file` — строки `пользователь:пароль`, права файла 600:

   ```
   backup:Parol123
   ```

   Для **цели** обязательно `read only = no` (иначе rsyncd отклонит
   запись). Без `auth users` доступ анонимный (тогда пароль в backupd
   не нужен).

2. Запустите демон:

   ```bash
   rsync --daemon --config=/etc/rsyncd.conf   # или через systemd:
   systemctl enable --now rsyncd
   ```

3. Брандмауэр: разрешите входящие TCP **порт 873** (на Windows —
   «Брандмауэр» → Входящие правила → порт 873).

4. В backupd: *Тип* → «rsyncd (демон rsync)», хост, порт (по
   умолчанию 873), модуль (как в конфиге), при необходимости
   подпуть внутри модуля и учётные данные.

Особенности rsyncd:

- Протокол rsyncd **не шифрует** передачу (в отличие от SSH) —
  используйте только в доверенной сети.
- При цели rsyncd `--link-dest` недоступен: снапшоты всегда
  полные копии (в журнале задания это отражается).
- Пароль rsyncd не попадает в команды и журналы: rsync получает его
  только из временного файла `--password-file` (права 600), который
  удаляется сразу после запуска.
- Перед копированием сервер проверяет доступность демона по TCP
  (порт 873) и записывает причину отказа в журнал задания.

## Вариант: FTP (lftp mirror)

Если на источнике (или на цели) стоит FTP-сервер, копирование можно
выполнять через утилиту [lftp](https://lftp.yar.ru/) (команда `mirror`)
вместо rsync. В интерфейсе: *Тип источника/цели* → «FTP-сервер
(клиент lftp)», хост, порт (по умолчанию 21), пользователь, пароль,
каталог на FTP-сервере (пустое поле — корень FTP-сервера, `/`).

Особенности FTP-варианта:

- Снапшоты и удержание **не применяются** — всегда **одна актуальная
  копия** в подкаталоге `mirror` (режим задания принудительно
  «Зеркало», выбор режима в интерфейсе блокируется).
- lftp работает только с локальным каталогом и другим FTP-сервером:
  комбинации FTP + SMB/SSH/rsyncd отклоняются при создании задания.
- Настройки lftp задаются в блоке «Настройки lftp» формы задания:
  - *Параллельные потоки* — сколько файлов копируется одновременно
    (`mirror --parallel=N`, по умолчанию 4);
  - *Потоков на файл (pget)* — 1 = выключено, >1 — каждый файл
    копируется несколькими соединениями (`mirror --use-pget-n=N`);
  - *Буфер передач, КиБ* — `xfer:buffer-size`; по умолчанию 1024
    (1 МБ) — результат бенчмарка мелких файлов (см. ниже), 0 —
    дефолт lftp (64 КБ);
  - *Только новые файлы* — `mirror --only-newer` (включено по
    умолчанию): копируются только файлы, изменившиеся на стороне
    источника после их копии; отключите, если нужно пересоздавать
    на цели файлы «старше» локальных;
  - *Продолжать незавершённые* — продолжение сравнением списков
    (выключено по умолчанию): при копировании формируется список
    всех файлов источника и список скопированных (локальная цель —
    свежий скан каталога цели, FTP-цель — карта, сохраняемая между
    прогонами в `data/ftp_state/<id>.json`). В случае неполного
    копирования списки сравниваются, и недостающие на цели файлы
    (или отличающиеся по размеру — обрезанные при обрыве)
    копируются повторно, целиком. Копирование идёт прямыми
    FTP-передачами (ftplib) в параллельных потоках («Параллельные
    потоки»), команда `mirror` не используется; обрезанный файл
    копируется заново с начала, а не докачивается (REST). Так
    работает кнопка ⏩ «Продолжить» (разовый прогон без «Только
    новые файлы», остальные опции задания сохраняются); с
    включённым чекбоксом этот алгоритм используют все прогоны
    задания (в т.ч. по расписанию) — повторный прогон
    доскопирует только появившиеся на источнике / изменившие
    размер файлы;
  - *Пассивный режим* — `ftp:passive-mode` (включён по умолчанию;
    отключите, если брандмауэр блокирует входящие данные).
- **Кириллические (и любые не-ASCII) имена файлов** копируются
  корректно: lftp запускается в UTF-8-локали системы (C.UTF-8 /
  C.utf8, либо любая другая доступная UTF-8-локаль — определяется
  автоматически при первом FTP-прогоне). Это обязательно: под
  `LC_ALL=C` lftp заменяет не-ASCII символы имён на «?» при
  отправке FTP-команд (RETR/DELE), сервер отвечает 550, и такие
  файлы не копируются (проверено: lftp 4.9.2 + FileZilla Server
  1.12.6).
- **Оптимизация под мелкие файлы** (бенчмарк lftp 4.9.2,
  `mirror --parallel=4`, FTP-сервер с ~300 000 мелких файлов,
  5 000+ каталогов; 90 с на конфигурацию, 2 раунда):

  | Конфигурация | Раунд 1 (файл/с) | Раунд 2 (файл/с) | Вывод |
  |---|---|---|---|
  | базовая (как была) | 82 | 65 | — |
  | `--verbose=0` | 81 | 36 | без эффекта (узкое место не вывод) |
  | `xfer:clobber true` | 78 | 60 | без эффекта (mirror и так сам удаляет старые файлы) |
  | `xfer:buffer-size 1 МБ` | **84** | **68** | стабильно чуть быстрее — стало дефолтом |
  | `--parallel=8` | 47 | — | заметно медленнее — сервер не масштабируется по потокам |

  Вывод: при мелких файлах «узкое место» — накладные расходы
  протокола на файл (соединение данных + LIST на каталог), а не
  пропускная способность; клиентские настройки дают лишь ~2–5 %.
  lftp 4.9.2 по умолчанию пишет файлы сразу в целевое имя
  (`xfer:use-temp-file no`) — временный файл + переименование
  не добавляются.
- Лимит скорости задаётся общим полем «Лимит скорости, КБ/с»
  (преобразуется в `net:limit-rate`, байт/с).
- Исключения (`--exclude-glob`) действуют как и для rsync.
- Пароль не попадает в командную строку и журнал: lftp запускается
  сценарием из временного файла `data/creds/<id>.lftp-script`
  (права 600, удаляется после прогона); в журнале пароль в URL
  замаскирован (`***`). В журнале задания записывается полная
  команда со всеми параметрами (без пароля), а копия сценария
  **без пароля** постоянно хранится в
  `data/scripts/<id>.lftp-script` (перезаписывается каждым
  прогоном) — для диагностики.
- Протокол FTP **не шифрует** передачу (включая пароли) —
  используйте только в доверенной сети. Шифрование (FTPS/SSL)
  отключено явно: `set ftp:ssl-allow no` в сценарии lftp —
  подключение всегда без шифрования.
- Права удалённых файлов не сохраняются
  (`set mirror:set-permissions no` в сценарии lftp): если сервер
  не поддерживает команды изменения прав (CHMOD/MFF), lftp 4.9.x
  при включённом подробном выводе считает это ошибкой и
  завершается с ненулевым кодом.
- Если источник — локальный каталог, а цель — FTP, источник
  передаётся lftp полным `file://` URL: с «голым» локальным
  путём при `ftp://`-цели lftp 4.9.x сам не подключается к
  серверу («mirror: Not connected»).
- **Прогресс копирования** во время прогона FTP-задания
  отображается в GUI: полоса, «N / M файлов», **скорость
  передачи** (МБ/с, средняя за прогон) и **оценка оставшегося
  времени** (максимум из двух оценок — по остатку байт и по
  остатку файлов; при многих маленьких файлах «узкое место» —
  накладные расходы на файл, а не байты). Источник для
  знаменателя просматривается **один раз**: локальный — один
  проход `os.walk`, FTP — одно дополнительное соединение и
  `LIST` по каталогам (без передач файлов; лимиты 100 000
  каталогов, 1 000 000 файлов, 1800 с — защита от аномально
  больших источников). Скан идёт **параллельно с копированием**
  и не задерживает старт прогона: пока итог считается, GUI
  показывает число скопированных файлов и пометку
  «итог определяется…», затем появляются полоса с процентом,
  скорость и ETA. Строка «Источник (итог для прогресса): …»
  (или причина сбоя скана) дописывается в журнал задания после
  завершения прогона. Сам процент считается по строкам
  «Finished transfer» уже стримируемого вывода lftp — без
  дополнительных запросов к серверу и без опросов. FTP-скан
  использует тот же режим данных, что и сам mirror (настройка
  `passive` задания), и при сбое делается одна повторная попытка
  (как повторные подключения у lftp). Если
  предварительный просмотр не удался, GUI показывает только число
  скопированных файлов (без процента), а в журнал задания
  записывается полная причина (лимит просмотра, таймаут
  контрольного или данных соединения и т. п.). Прогресс живёт
  только в памяти (в
  `state.json` не пишется) и убирается после завершения задания.
> **Расширенное логирование FTP** включается ключами запуска
> сервиса, уровень подробного вывода операций `mirror` зависит от
> ключа:
> - **без `-v`** — подробные операции с файлами и директориями,
>   планируемые команды dry-run и детали подключения в журнал
>   задания не пишутся (тихо). lftp при этом запускается не с
>   `--verbose=0`, а с `--verbose=2`: строки
>   «Transferring/Finished transfer» из этого вывода используются
>   для процента прогресса в GUI, в журнал задания их
>   отфильтровывает сервер. Тестовый прогон (dry-run) — с
>   `--verbose=0`: lftp печатает планируемые команды независимо
>   от уровня, сервер их отфильтровывает;
> - **`-v`** — в журнал попадают только операции с директориями
>   («Mirroring directory», «Making directory», «Finished mirror»,
>   «Removing old directory»), dry-run-команды с каталогами
>   («mkdir …», «rm -r …»), детали предпроверки и протокол
>   подключения lftp;
> - **`-vv`** — все подробные операции, включая файловые
>   («Transferring file», «Finished transfer», «Removing old file»),
>   и все dry-run-команды («get -O …», «chmod -f …», «rm …»).
>
> Базовые строки (команда, параметры, ошибки, сводка, результат)
> пишутся в любом случае.

- Перед копированием сервер проверяет подключение к каждому
  FTP-серверу по шагам. При запуске с `-v`/`-vv` в журнал задания
  записываются: IP-адрес (DNS-разрешение), время TCP-соединения,
  приветственный баннер сервера (220); при недоступности — причину
  отказа (запись ошибки остаётся и без `-v`).
- При запуске с `-v`/`-vv` этап подключения к FTP логируется
  подробно: lftp работает с включённым журналированием
  (`log:enabled`, `log:level 9`, `log:show-time`), и выдержка
  протокола до начала передачи файлов (все параллельные
  соединения, вход в систему, пассивный режим, первичные списки
  каталогов) с длительностью этапа попадает в журнал задания. В
  протоколе пароль маскируется (`***`); сам lftp в своём журнале
  записывает `PASS XXXX`. Временный файл журнала lftp
  (`data/creds/<id>.lftp-log`) создаётся только с `-v`/`-vv` и
  удаляется после прогона.
- `lftp` не требуется для остальных вариантов: при его отсутствии
  сервер запускается с предупреждением в консоли, FTP-задания
  отклоняются с понятной ошибкой. Установите:
  `apt install lftp` (Debian/Ubuntu) или `dnf install lftp`
  (RHEL/Rocky/Alma).
- Остановка прогона кнопкой «Остановить» — не ошибка: статус
  задания «остановлено» (янтарный бейдж в списке и истории),
  в отчёте «Ошибки копирования: нет». Если в момент остановки
  шёл transfer, в журнал задания пишется список файлов, чья
  передача была прервана (строка «Прерваны передачи N …» + до
  50 имён) — такие файлы на цели могут оказаться обрезанными.
  Кнопка ⏩ «Продолжить» (или прогон с опцией «Продолжать
  незавершённые») сравнивает списки «источник − скопировано» и
  копирует недостающие файлы без mirror: обрезанный файл в
  списке «скопировано» отсутствует (или имеет другой размер),
  поэтому копируется заново целиком — обрезки чинятся без
  зависимости от mtime и `--only-newer`.

## Как создаются копии

Для задания `test` с источником `/var/data` на диске Windows будет:

```
D:\Backup\test\
├── 20261005_020000\      <- снапшот (полный, первый)
├── 20261006_020000\      <- снапшот (инкрементальный: изменённые файлы
│                             скопированы, остальные — жёсткие ссылки)
├── 20261007_020000\
└── ...
```

- Каждый снапшот — **самостоятельная** копия: можно открыть любой прошлый
  день и восстановить файлы, не трогая остальные.
- Объём инкрементальных снапшотов ≈ только изменение данных.
- По политике удержания (например, последние 7 снапшотов + 7 дней / 4 недели /
  6 месяцев) старые снапшоты удаляются автоматически.
- Раз в `full_every_days` дней (по умолчанию 7) снапшот делается
  полностью — защита от накопления ошибок и ускорение восстановления.

## Отчёт о выполнении заданий

После **каждого** завершения задания (обычный прогон, тестовый dry-run,
успех или ошибка) в файл `data/reports/report.txt` дописывается запись:

```
============================================================
Задание: test
Прогон: обычный | режим: incremental
Начало: 2026-11-07 02:00:00
Завершение: 2026-11-07 02:04:12
Длительность: 252.3 с
Скопировано файлов: 137
Размер скопированных файлов: 412.7 МБ
Средняя скорость: 1.7 МБ/с
Ошибки копирования: нет
============================================================
```

Статистика (количество файлов, размер, скорость) берётся из вывода
`rsync --stats`; при ошибке до/вместо копирования в поле «Ошибки
копирования» записывается текст ошибки (например, ошибка монтирования
SMB или код завершения rsync с его сообщениями). Запись о задаче
отражается в журнале задания строкой «Отчет: <путь к файлу>».

## Push-уведомления (ntfy)

О начале и о завершении **каждого** задания (успех, ошибка, остановка и
тестовый прогон) можно получать push-сообщения на своё устройство:
**Android** — приложение «ntfy» (Play Store / F-Droid), **Linux** — ntfy
desktop (или любой скрипт, подписанный на топик), **Windows** — «ntfy for
Windows».

Серверу не нужны никакие SDK — отправляется один HTTP POST на
`<сервер>/<топик>` (stdlib). Сервер ntfy может быть:

- публичный `https://ntfy.sh` — устройство подключается через интернет
  (работает, даже если устройство вне локальной сети);
- собственный в локальной сети, например
  `http://192.168.1.100:2000` (Docker: `ntfy/ntfy`, порт 2000) — тогда
  уведомления ходят только по LAN.

Настройка — вкладка «Система» → «Push-уведомления (ntfy)»: адрес сервера,
топик (создаётся случайным), включение/выключение и кнопка «Отправить
тест». В приложении ntfy нужно подписаться на тот же сервер и топик.

Содержимое сообщений (по-русски):

- **Начало**: «Начало: <имя задания>» + строки «Источник: …» и «Цель: …»;
- **Успех**: «Завершено: <имя>» + «скопировано N файлов, X · T с» (✅);
- **Остановка**: «Остановлено: <имя>» + длительность (⏸️) — не ошибка;
- **Ошибка**: «Ошибка: <имя>» + текст ошибки, приоритет *urgent* (❌).

Уведомления отправляются **асинхронно** после записи журнала и отчёта:
сбой ntfy-сервера или отсутствие интернета не влияет на копии и на
отчёт. В самих сообщениях пароли не содержатся (метки концов — без
паролей). Топик — как пароль: тот, кто его знает, читает уведомления,
поэтому используйте случайный топик и не публикуйте его.

Не-ASCII символы в заголовках **Title** и **Tag** сообщений передаются
в кодировке RFC 2047 (`=?UTF-8?B?…?=`), которую ntfy декодирует
нативно: кириллица и эмодзи отображаются на устройстве корректно
(percent-encoding в заголовках ntfy не декодирует — он отобразился бы
буквально).

## REST API (для интеграции)

Все запросы — JSON. Если задан пароль, защищённые запросы требуют заголовок
`Authorization: Bearer <токен>`; токен выдаётся при входе:

```bash
TOK=$(curl -s -X POST localhost:8420/api/login \
       -d '{"password": "…"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["token"])')
curl -s -H "Authorization: Bearer $TOK" localhost:8420/api/jobs
```

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/login` | `{"password": "…"}` — вход, выдаёт токен сессии (12 ч) |
| POST | `/api/logout` | завершить текущую сессию |
| GET | `/api/auth` | публично: включён ли пароль и авторизован ли запрос |
| POST | `/api/password` | `{"password": "…"}` — задать/сменить пароль (от 4 символов) |
| POST | `/api/password/clear` | отключить авторизацию |
| GET | `/api/notify` | настройки push-уведомлений (ntfy) |
| POST | `/api/notify` | `{"enabled", "url", "topic"}` — сохранить настройки ntfy |
| POST | `/api/notify/test` | отправить тестовое push-сообщение |
| GET | `/api/status` | статус сервера, версии rsync и lftp |
| GET | `/api/jobs` | список заданий со статусами |
| POST | `/api/jobs` | создать задание |
| PUT | `/api/jobs/<id>` | изменить задание |
| DELETE | `/api/jobs/<id>` | удалить задание |
| POST | `/api/jobs/<id>/run` | запустить (`{"dry": true}` — тест) |
| POST | `/api/jobs/<id>/stop` | остановить текущий запуск |
| POST | `/api/jobs/<id>/toggle` | включить/выключить задание |
| GET | `/api/jobs/<id>/log?tail=N` | хвост журнала |
| GET | `/api/jobs/<id>/snapshots` | список снапшотов |
| GET | `/api/history` | история запусков |

Старый статический токен (`auth_token` в `config.json`) по-прежнему
признаётся как `Bearer`-токен для обратной совместимости, но в интерфейсе
управление им больше не отображается.

## Безопасность

- По умолчанию интерфейс слушает **только 127.0.0.1** — наружу его не видно.
- При доступе извне задайте пароль (вкладка «Система» → «Задать / сменить
  пароль»). Пароль хранится в `config.json` только в виде scrypt-хеша;
  сессия живёт 12 часов и выдаётся после входа (`/api/login`).
  Авторизацию можно отключить кнопкой «Отключить авторизацию».
- Пароли SMB хранятся в `config.json` (права 644 по умолчанию — ограничьте:
  `chmod 600 data/config.json`), файл учётных данных для mount создаётся
  с правами 600 и удаляется сразу после монтирования.
- Для SSH-цели используется ключевая аутентификация (пароли не хранятся).
- Пароль rsyncd не передаётся в командной строке: rsync получает его
  только из временного файла `--password-file` (права 600, создаётся
  в `data/creds/` и удаляется сразу после запуска).
- Пароль FTP (lftp) не передаётся в командной строке: lftp запускается
  сценарием из временного файла `data/creds/<id>.lftp-script` (права 600,
  удаляется сразу после запуска), в журнале пароль в URL замаскирован.
  Учтите: протокол FTP передаёт пароли в открытом виде — только доверенная
  сеть.
